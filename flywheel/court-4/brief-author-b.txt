## What to write
Category: STRUCTURE AND DATA (a static scene that is wrong, with no dependence on events over time). That means: node placement and containment, DEF/USE, geometry (indices, counts, winding, normals, colours and texture coordinates per vertex or per face, degenerate or non-manifold data, Extrusion/ElevationGrid/NURBS parameters), field values, ranges and units (angles in radians, colours 0 to 1, unit rotation axes, scales), appearance and materials (Material, PhysicalMaterial, textures, texture transforms), lights, viewpoints and navigation, grouping/transform hierarchy and bounding boxes, LOD/Switch static settings, Inline and URLs, metadata, units, profile and component declarations, Proto declarations and instances.

Write, as X3D 4.0 XML files (complete documents with XML declaration, DOCTYPE optional, `<X3D profile=... version='4.0'>`, head, Scene). Declare the profile and the component statements each scene really needs under the X3D 4.0 standard (for example `profile='Immersive'` plus a `<component>` line for anything Immersive lacks), unless a wrong declaration IS the planted mistake:
1. `fault-01.x3d` … `fault-20.x3d`: 20 small scenes (roughly 15 to 80 lines), each with exactly ONE planted mistake that makes the scene look or load differently from what its author plainly intended. Make the intent obvious from DEF names and a `<meta name='description'>` that states the intent WITHOUT naming the mistake. Spread across families: at most 2 faults of the same family. Mix severities: some that break the standard outright, and at least half that are legal X3D (schema-valid) that renders wrong. Mix subtlety: some obvious, some that an expert would miss on a first read.
2. `twin-01.x3d` … `twin-20.x3d`: for each fault, the minimal corrected scene (the same file with only the mistake fixed). Each twin must look as the description says.
3. `decoy-01.x3d` … `decoy-05.x3d`: 5 scenes that look suspicious to a hasty reviewer but are correct X3D 4.0 and render as their description says (unusual but legal constructs).

## Checks you must run yourself
- Every file is well-formed XML (lxml).
- XSD: validate every file against kit/xsd/x3d-4.0.xsd with lxml (`etree.XMLSchema(etree.parse(path))`, it loads). Twins and decoys MUST be XSD-valid. Faults may or may not be; record which.
- X_ITE witness (do it for as many pairs as your time allows, and for ALL decoys): Chromium and Playwright are pre-installed (`require('playwright')` works from any directory in Node 22; `chromium.launch()` needs no options; do not install anything). Serve your folder plus the kit over a local http server, load a page with `<x3d-canvas>` using kit/x_ite/x_ite.min.js, load the scene, and compare fault against twin: screenshot both at the same size and report the fraction of pixels that differ, and/or read values through the X_ITE SAI (`canvas.browser`, `browser.currentScene`), and collect console errors and warnings. The twin should show the intended picture and the fault should differ (or log an error). Decoys must load with zero console errors and draw something. Be honest: if a "fault" turns out to render the same as its twin in X_ITE, either replace it or keep it and mark `engine_disagrees: true` with the reason (some faults are real but invisible in one engine).

## Manifest
