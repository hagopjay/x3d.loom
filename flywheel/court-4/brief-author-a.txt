You are the blind author of a sealed test set for an X3D checker. You write the test; someone else, who must not see it yet, is changing the checker. Your value comes from NOT knowing what the checker checks.

- Work ONLY inside WORK/author-a/ (your folder) and read ONLY WORK/kit/ (neutral kit: the public X3D 4.0 XSD in kit/xsd/x3d-4.0.xsd, and the complete X_ITE 16.8.0 distribution in kit/x_ite/, with every component file under kit/x_ite/assets/components/, so any profile and component loads). - Do not try to guess what the checker catches, and do not design faults to beat it or to flatter it. Write the mistakes you believe matter most in real X3D written by an AI model or a hurried person.

## What to write
Category: BEHAVIOUR. That means anything about what a scene does over time or on interaction: ROUTEs, event types and access types, TimeSensor and clocks, interpolators and sequencers, triggers/toggles/filters, followers (chasers/dampers), pointing and drag sensors, environment sensors (Proximity, Visibility, Collision), key sensors, Switch/LOD driven by events, Script nodes, animation loops, start/stop/pause timing, viewpoint binding, load sensing.

Write, as X3D 4.0 XML files (complete documents with XML declaration, DOCTYPE optional, `<X3D profile=... version='4.0'>`, head, Scene). Declare the profile and the component statements each scene really needs under the X3D 4.0 standard (for example `profile='Immersive'` plus a `<component>` line for anything Immersive lacks), unless a wrong declaration IS the planted mistake:
1. `fault-01.x3d` … `fault-20.x3d`: 20 small scenes (roughly 20 to 80 lines), each with exactly ONE planted mistake that makes the scene behave differently from what its author plainly intended. Make the intent obvious from DEF names and a `<meta name='description'>` that states the intent WITHOUT naming the mistake. Spread across families: at most 2 faults of the same family. Mix severities: some that break the standard outright, and at least half that are legal X3D that plays wrong or does nothing useful. Mix subtlety: some obvious, some that an expert would miss on a first read.
2. `twin-01.x3d` … `twin-20.x3d`: for each fault, the minimal corrected scene (the same file with only the mistake fixed). Each twin must do what the description says.
3. `decoy-01.x3d` … `decoy-05.x3d`: 5 scenes that look suspicious to a hasty reviewer but are correct X3D 4.0 and behave as their description says (unusual but legal constructs).

## Checks you must run yourself
- Every file is well-formed XML (lxml).
- XSD: validate every file against kit/xsd/x3d-4.0.xsd with lxml (`etree.XMLSchema(etree.parse(path))`, it loads). Twins and decoys MUST be XSD-valid. Faults may or may not be; record which.
- X_ITE witness (do it for as many pairs as your time allows, and for ALL decoys): Chromium and Playwright are pre-installed (`require('playwright')` works from any directory in Node 22; `chromium.launch()` needs no options; do not install anything). Serve your folder plus the kit over a local http server, load a page with `<x3d-canvas>` using kit/x_ite/x_ite.min.js, load the scene, and use the X_ITE SAI (`canvas.browser`, `browser.currentScene.getNamedNode(...)`) to sample the field the description is about over a few seconds of simulated or real time (for pointing sensors you may dispatch real mouse events, or mark the witness as reasoned). The twin should show the intended behaviour and the fault should not. Decoys must load with zero console errors. Be honest: if a "fault" turns out to behave fine in X_ITE, either replace it or keep it and mark `engine_disagrees: true`.

## Manifest
Write `MANIFEST.json`: an object keyed by file name. For each fault: `{"category": "...family...", "fault": "one sentence naming the mistake", "viewer_sees": "what a viewer observes", "spec": "error per the X3D standard (say which rule)" | "legal, plays wrong", "xsd_valid": true|false, "witness": "x_ite-16.8.0" | "reasoned", "witness_note": "what you measured, e.g. translation.y stayed 0 over 3 s; twin reached 2.0", "twin": "twin-NN.x3d"}`. For each twin and decoy: `{"category", "intent", "xsd_valid": true, "witness", "witness_note"}`; decoys add `"why_suspicious"`.
Also keep your witness harness script and its raw output (`witness.json`) in the folder.
