# Learnings: the Loom for glTF 2.0 (20 Nov 2026)

Lane: `formats/gltf/` (scope and numbers in `formats/gltf/SPEC.md`). Instruments: Chromium 157.0.8103.78 headless on SwiftShader (no GPU), Khronos glTF-Validator 2.0.0-dev.3.10, Khronos Sample Renderer 1.1.0, three r187, Babylon 9.32.0, X_ITE 16.7.1, Blender 5.3.0 Cycles (bpy, CPU, 64 spp). 7 Khronos sample assets x 4 engines = 28 scored runs, plus 3 project X3D scenes through the semantic bridge.

1. **glTF pins the BRDF and nothing around it.** No light, no default view, no ambient, no display encode in core. A glTF render is only judgeable after a harness pins camera, one KHR_lights_punctual light, no IBL, no tone map and the clear colour. X3D stays the reference format because ISO 19775-1 defines the picture end to end (Confirmed, spec text).
2. **The reference renderer is not normative.** Khronos Sample Renderer 1.1.0, Babylon 9.32.0 and X_ITE 16.7.1 encode with pow(1/2.2); three r187 and Cycles use the sRGB curve. Judge after re-encoding to the reference's encode: three's Box goes from 35.83 to 48.10 dB, its DamagedHelmet from SSIM 0.9686 to 0.9893 (Confirmed, source read + receipts).
3. **All five renderers share the 1/pi light convention.** A 2.5 lux sun lights the red Box within 1-6 levels in every engine. Blender's glTF importer default `SPEC` divides lux by 683; use `COMPAT` (Confirmed).
4. **X_ITE is the closest engine to the Khronos reference** on 5 of 7 assets, bit-identical on Box (Confirmed). Outliers: Babylon on NormalTangentMirrorTest (SSIM 0.915, specular on the mirrored panel, cause Suspected), X_ITE on AlphaBlendModeTest (0.958, texture filtering Suspected).
5. **A path tracer is a witness, not a candidate.** Cycles fails 4/7 because it draws shadows the raster engines do not (Confirmed by eye on the contact sheet).
6. **Score the candidates against each other.** On the converted Walking Twin, three/Babylon/X_ITE agree at SSIM >= 0.9993 while all fail against Khronos: the reference was the outlier on normal-less meshes. The receipt now says `reference-suspect` in that case (rule R-GLTF-8).
7. **X3D meaning survives glTF as JSON-LD.** Metadata trees → KHR_xmp_json_ld with `@list` values (JSON-LD arrays are unordered), lifted IRIs (`crm:E22`, `ifc:IfcBeam`, `loom:ifcGlobalId`) never read back. Walking Twin: 192 metadata nodes and 24/24 IFC ids round-trip lossless; Giza: 9/9 CIDOC-CRM refs (Confirmed, rules S0-S7, each with a mutation test).
8. **The validator is blind to KHR_xmp_json_ld** (2.0.0-dev.3.10 reports UNSUPPORTED_EXTENSION at INFO). The semantic gate must check packet structure itself (S0).
9. **Receipts sealed in JS and checked in Python must print floats the JS way** (0.000011, not 1.1e-05); the first check flagged a false drift on DamagedHelmet.
10. **The VVL lane and this lane converged on one block.** x3d.wgpu `x3d-wgpu-conformance/2` writes `gpu` + `api_validation` with the same names as `loom.render-receipt/1`, so one reader handles X3D, glTF and native Vulkan receipts.
