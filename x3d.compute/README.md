# x3d.compute: WebGPU compute (WGSL) for X3D workloads

Five compute kernels that move the per-frame arithmetic of five X3D features onto the GPU, each with an X3D fixture, an independent CPU reference and a correctness gate, plus a benchmark harness that measures with GPU timestamps, wall clock and a real `requestAnimationFrame` loop. It sits beside the bridges and changes none of them: nothing under `x3d.webgpu/` or `x3d.threejs/` is edited, and the shared reader is only read (the fixtures use the same node and field names the reader parses).

| kernel | X3D feature | one thread is | reference it must match |
|---|---|---|---|
| `src/kernels/particles.wgsl` | `ParticleSystem`: `ConeEmitter`, `ForcePhysicsModel`, `WindPhysicsModel`, `BoundedPhysicsModel` floor | one particle | `src/ref/particles.js`: same pcg hash, same f32 order of operations |
| `src/kernels/skinning.wgsl` | `HAnimHumanoid` / `HAnimJoint` skinCoord linear blend skinning, 4 influences | one vertex | `src/ref/skinning.js`: forward kinematics + CPU blend |
| `src/kernels/volume.wgsl` | `VolumeData` with `OpacityMapVolumeStyle` or `ProjectionVolumeStyle` MAX | one pixel (ray) | `src/ref/volume.js`: same nearest-voxel march |
| `src/kernels/nurbs.wgsl` | `NurbsPatchSurface` tessellation, rational, analytic normals | one grid vertex | `src/ref/nurbs.js`: a different algorithm (recursive Cox-de Boor, f64) |
| `src/kernels/splats.wgsl` | `GaussianSplats`: EWA projection, culling, depth sort (bitonic network) | one splat / one compare-exchange | `src/ref/splats.js`: f64 projection and a CPU sort of the GPU's own keys |

## Run it

```sh
# Chromium with WebGPU + playwright on the machine (NODE_PATH or local install); no GPU needed, SwiftShader is the default adapter
node tools/make-fixtures.mjs                          # regenerate fixtures/*.x3d (deterministic)
node tools/run.js --quick                             # 2 sizes per kernel, about 35 s on 4 cores
node tools/run.js --name=full-swiftshader             # everything, writes receipts/full-swiftshader.json
node tools/run.js --gpu --name=full-mygpu             # real adapter: no SwiftShader flags; this is the run that needs a real GPU
node tools/run.js --only=splats,volume                # a subset
./tools/mutation-check.sh                             # plants one bug per kernel; every mutant must turn its suite red
```
Exit code is non-zero when any suite fails, any WebGPU error fires, or the page throws.

## How a result is measured

* **GPU ms**: `timestamp-query` around the first and last compute pass of one workload (median and p95 of 12-15 runs after warm-up). Present on SwiftShader, where it measures CPU-emulated execution, so it is a correctness-and-scaling number, not a GPU number.
* **Wall ms**: `submit()` to `onSubmittedWorkDone()`.
* **rAF**: one workload per animation frame for 90 frames (fewer when the workload is slow). Three numbers are kept apart on purpose: `rAF_dt` (what a naive frame counter reads), `sustained_ms_per_frame` (first frame to last completed frame, the honest figure) and `submit_to_done_ms`. When compute takes longer than a vsync interval, rAF keeps ticking at the display rate while the queue backs up, so only the sustained figure tells the truth. The bridge test harness stubs frames at 300 ms; none of these numbers come from that path.
* Every receipt (`receipts/*.json`) carries the rig: Chromium version, adapter, flags, CPU count, timestamp support.

## Layout

| path | what |
|---|---|
| `src/gpu.js` | device init, buffer helpers, `bench()`, `compare()` / `compareRel()` |
| `src/kernels/*.wgsl` | the five kernels |
| `src/ref/*.js` | CPU references and the X3D fixture readers (`fromX3D`) |
| `fixtures/*.x3d` | six fixtures, generated by `tools/make-fixtures.mjs` |
| `bench/page.js`, `bench/index.html` | the harness page (correctness first, then timing) |
| `tools/run.js` | headless runner and receipt writer |
| `tools/mutation-check.sh` | proves the gates can fail |
| `receipts/` | recorded runs |

The measurements, the heuristics they support and the honest limits are written up in the x3d.docs chapter "WebGPU compute for X3D".
