# Sound on the Babylon bridge: how to compare Web Audio, and what was found

Scope: the 19 nodes of the X3D 4.0 Sound component that the bridge had only compared by settings and clocks: Analyser, AudioDestination, BiquadFilter, BufferAudioSource, ChannelMerger, ChannelSelector, ChannelSplitter, Convolver, Delay, DynamicsCompressor, Gain, ListenerPointSource, MicrophoneSource, OscillatorSource, PeriodicWave, SpatialSound, StreamAudioDestination, StreamAudioSource, WaveShaper. (AudioClip and Sound are baseline nodes and were not part of the lane.) Receipts: BATCH-38.md to BATCH-41.md.
Reference engine: X_ITE 16.6.0 (its source `dist/x_ite.js` was read, its behaviour measured by driving it). Rig for every number below unless a line says otherwise: Chromium 153.0.8010.12 (Chrome for Testing), headless, SwiftShader (no GPU), Babylon.js 9.32.0, X_ITE 16.6.0, a realtime AudioContext at 44100 Hz, flags `--autoplay-policy=no-user-gesture-required --use-fake-device-for-media-stream --use-fake-ui-for-media-stream --use-file-for-fake-audio-capture=<1 kHz wav>`. No sound card: the output device is Chromium's null sink.

## The method in one paragraph

Both engines run in the same browser build and build their graphs on that page's own AudioContext, so the Web Audio DSP is literally the same code in both. What can differ is the graph the bridge builds (which nodes, which parameters, which order). The test therefore records what comes out of each X3D node (`tools/audio-probe.js`, injected into both pages by `tools/run-tests.js`) and measures it with phase independent numbers: rms, peak, fundamental frequency, amplitude of the harmonics at the exact frequency (Hann window), rms in frequency bands, onset lag, and correlation within +-8 samples. Each spec states what the number must be (computed from the Web Audio specification, or taken from a node of the browser itself made on the page with the same parameters) and a list `agree` of numbers that must match between the engines with a tolerance. Steps that only one engine can answer are marked `only: "ours"` or `only: "xite"`.

Step vocabulary (all in the spec JSON, header of `tools/audio-probe.js`): `tap` (record a node's output; an array of nodes records one channel each, sample aligned), `sig` (measure a tap, optionally with an `expect` object like `{rms:[0.7071,0.02], f0:[1000,3], silent:true}`), `fsig` and `bytemap` (an Analyser's data fields), `amap` (a page expression stored as a number or an object of numbers; `scene` and `AUD.ctx` are in scope), `close` (two stored numbers within a tolerance), `untap`. Note the name `amap`: it started as `jsmap` and collided with a different `jsmap` step that came in with the HAnim batch (it ran first in the dispatch and the audio specs failed with "scene is not defined"). If you add a step to `run-tests.js`, grep the dispatch for the name first.

## Traps (each one cost a failed run)

1. **Autoplay.** An AudioContext starts suspended without a user gesture. The rig passes `--autoplay-policy=no-user-gesture-required`; a real page needs a click or key, and that is the browser's rule, not the bridge's. Both engines resume the context themselves when it is allowed to.
2. **Sample rate.** The context runs at 44100 Hz here (not 48000). Anything that depends on it (a delay of 441 samples = 10 ms, the Convolver impulse built "at the context's rate", the data of a decoded file) must read `AUD.sr()` or be written as time, never as a sample count in the spec. A file decoded with `decodeAudioData` is resampled to the context rate: the 1600 sample 8 kHz test wav reads back as sampleRate 44100, bufferLength 8820 in both engines.
3. **No offline rendering.** The first plan was an OfflineAudioContext. It does not work: both engines create their AudioContext inside the page (X_ITE `getAudioContext()`, ours `BR.audio.ctx()`), shared by every node, so the only way to compare is to record the realtime graph. Everything is therefore timing tolerant: windows are taken relative to the end of a `settle`, an onset is searched after a threshold, and levels are measured as rms over a window, not sample by sample.
4. **ScriptProcessorNode drops chunks** when the page is busy (the Babylon scene on SwiftShader is slow). The recorder is an AudioWorklet (`rec-tap`) on the audio thread with a frame number on every block, so two taps line up exactly and never lose samples.
5. **A node nobody pulls is not rendered.** Web Audio freezes the state of a node that has no path to the destination (a Delay line stops moving). Every tapped node therefore also feeds a muted gain into the destination ("sink"), and the tap is removed again at the end of the step. Without this the second delay test read lag 0 in both engines.
6. **Do not disconnect everything.** `node.disconnect()` with no argument also drops the tap, and any other listener. SpatialSound did this on every property change (now `disconnect(destination)` only), which showed up as silence in the recording only.
7. **State leaks between steps.** A property left from an earlier step (frequency 0, gain 0.25, a loop flag) changes the next measurement. Each signal case starts a fresh node of the fixture or sets everything it depends on first; the measurement window must also start after the settle of the last change (a window across a frequency change gives a smeared f0).
8. **The `env.sh` trap.** The shell helper in the test rig `cd`s into the main checkout. Running `npm test` or `run-tests.js` from a second worktree after `source env.sh` and `cd` silently tests the other checkout ("33/33 passed" for code that was not there). Source first, then `cd`, and print `pwd`.
9. **Parallel runs.** Four browsers at once crashed one page ("Target crashed"). Three in parallel are fine. A bad step spec (a tap whose channel option was an object inside an object) also crashed the page and looked like a browser problem.
10. **The Convolver `normalize` flag is read when the buffer is set**, in the browser itself: setting `normalize` after the buffer does nothing. Set normalize first, then the buffer, in the spec; both engines then agree with a ConvolverNode made on the page the same way.
11. **Capture processing eats a test tone.** With default constraints Chromium's noise suppression and gain control take a steady 1 kHz fake microphone from rms 0.44 to 0.04 in three seconds. Both engines call `getUserMedia({audio:{deviceId}})` with no processing switches (X_ITE does it that way, the bridge copied it), so the rig wraps `getUserMedia` in an init script (`MICFIX` in `run-tests.js`) for every page and switches echoCancellation, noiseSuppression and autoGainControl off. With that the fake microphone reads rms 0.3536 (amplitude 0.5) steadily. `getUserMedia` also needs the fake-ui flag and a secure context (the rig serves from localhost).
12. **A stale gap note.** The Analyser note said "nothing is wired into the analyser yet": the node was wired in batch 13 already. Notes are checked against the code when the node is reopened.
13. **MFString fields.** `streamIdentifier` of the Stream* nodes is an MFString (a list), not an SFString.

## X_ITE 16.6.0 behaviour that the bridge copies (or does better)

1. Per node X_ITE builds an input gain (`audioDestination`: gain, channelCount, mode, interpretation), the processing node (`soundProcessor`) and an output gain (`audioSource`); the bridge has the same three stages (`n._au.in / proc / out`), which is what the taps read on both sides.
2. **BiquadFilter.** `gain` of the X3D node is the input stage. The biquad's own gain (the dB that makes PEAKING and the shelves boost or cut) is never set in X_ITE, so those three types are flat in both engines. `qualityFactor` is passed in dB for LOWPASS and HIGHPASS (Web Audio's Q is in dB there), as X_ITE does and the bridge copies. Not fixed in either engine: it would no longer match.
3. **OscillatorSource.** Square, sawtooth and triangle waves come from the browser's built-in band limited tables, peak normalised: a square of amplitude 1 reads rms 0.843, a sawtooth 0.485, not the ideal 1.0 and 0.577. The specs compare against an OscillatorNode of the page (the browser's own wave) and against the harmonic ratios, not against ideal formulas. `set_stop` fades for 30 ms; `set_pause` is `set_stop` and `set_resume` is `set_start` (a paused oscillator restarts from phase 0).
4. **PeriodicWave** `real/imag` and `type`: a live change reaches a running oscillator in X_ITE. The reader did not (it kept the wave it was started with). Fixed in `src/nodes/PeriodicWave.js`.
5. **OscillatorSource gain while running.** The reader applied `gain` only at start; fixed (`src/nodes/OscillatorSource.js`).
6. **Analyser.** The four data fields are refreshed once per frame while the node is active (the test rig draws about three frames per second in our reader, 60 in X_ITE), from the last `fftSize` samples at that moment. Single samples are therefore never compared, only rms, frequency, correlation and the peak bin. `smoothingTimeConstant` is read back from the audio node, not measured as a time response.
7. **DynamicsCompressor** `reduction` is read once per frame; its time response (attack and release as functions of time) is not compared, only the settled level and the settled reduction. Web Audio adds a makeup gain and a look-ahead of about 6 ms that no X3D field controls.
8. **Delay / Convolver** `maxDelayTime` outside 0..180 s: X_ITE throws; the bridge holds it to 0.001..179.999 and keeps the node. A Convolver response with 3 channels, or more than 4, is refused by Web Audio; the bridge keeps the previous response.
9. **SpatialSound / ListenerPointSource.** The panner gets a *stereo* input in both engines (a mono source is up-mixed to two equal channels before the panner), so the Web Audio **stereo** panning applies, not the mono one: a source far to the left comes out in the left ear at twice the mono level (rms 0.2747 against 0.1373 at 5.1 distance for a 1 kHz sine of rms 0.7071). The probe's `AUD.panGain` has this model (with `mono=true` for the other one). The listener and the panner live in the camera's own space (listener at the origin looking down -z); the node's pose is taken through the view matrix once per frame. X_ITE plays a SpatialSound only while it is drawn (its traversed flag); the bridge plays it whenever it is enabled. The HRTF model is compared with X_ITE only (left ear louder than the right, 0.0288 against 0.0132 here), not with a formula.
10. **ChannelMerger / ChannelSplitter / ChannelSelector.** Disabled, a ChannelMerger is not there at all: all children are added into channel 0 (rms 1.2247 for three equal sines of 0.7071) and the other channels are silent; a disabled ChannelSplitter hands the unsplit stereo signal to every output node. Both are the same in X_ITE and the bridge. More than 32 children are not connected (not tested).
11. **AudioDestination** goes through a `MediaStreamAudioDestinationNode` into an `<audio>` element in X_ITE, and `mediaDeviceID` is `audioElement.setSinkId(id)`. The bridge now does the same when the id is not empty (default output otherwise): in the rig `default` is accepted and a made up id is refused with a SecurityError ("No permission to use requested device"), the error goes to the console and the signal stays on the default output. Which loudspeaker a real device id reaches cannot be seen in a headless browser and is not compared.
12. **StreamAudioSource / StreamAudioDestination** are "not supported" in X_ITE 16.6.0: the fields are held, the clock of the source runs, the destination never sets `isActive`, no sound is made and no stream exists. The bridge went beyond that (the spec describes working nodes): a StreamAudioDestination makes a MediaStream and publishes it under every name of `streamIdentifier` in `BR.snd.streams` (a Map the page can also read and write: `__bridge.snd.streams.set('name', mediaStream)` for a WebRTC or getUserMedia stream); a StreamAudioSource plays a stream under one of its names while it is active (it keeps looking each frame until the stream exists, lets go on pause and stop). These two are therefore compared with the Web Audio specification, in our reader only (steps marked `only: "ours"`), and with X_ITE on the fields and the clock.

## Tolerances and what was measured (rig above)

Because both engines run the same Chromium Web Audio code, the engines agree to better than 1e-4 (relative to max(1, |X_ITE value|)) on every `agree` number except the compressor's `reduction` read-out; the tolerances in the specs are the claim ("the bridge is right if it is within this of the reference"), not the observed spread. The spec bounds, as written in the `*.test.json` files:

| node | what is compared | bound |
|---|---|---|
| Gain | rms of a 1 kHz sine (0.7071) at gain 0.25 / 2 / 0 / -1 / disabled; correlation with the input | rms +-0.01 (+-0.03 at gain 2); corr +-0.02 (gain -1 reads -1) |
| Delay | onset lag at delayTime 0 / 0.1 / 0.25 / 0.4 s | +-0.006 s (one 128 sample render block is 0.0029 s) |
| OscillatorSource | sine, triangle, sawtooth, square, custom wave: rms and harmonics; frequency, detune, gain; stop, pause, resume | rms +-0.02 (+-0.03 square), harmonics +-0.03, f0 relative 0.003 to 0.005 |
| PeriodicWave | real / imag harmonic amplitudes, the four built-in types, live change of a running oscillator | harmonics +-0.03, rms +-0.02 |
| Analyser | rms, f0, correlation of float and byte time data; peak bin of float and byte spectra; byte vs float data | rms +-0.03, f0 +-1 %, corr +-0.02, byte vs float <= 3 steps (maxErr +-0.02 of full scale), peak bin +-1 % |
| BiquadFilter | rms of a sine through 8 filter types at several frequencies against |H(f)| from the specification's coefficients; Q, detune, disabled | +-0.012 (+-0.02 disabled) |
| DynamicsCompressor | settled rms and `reduction` for four threshold/knee/ratio cases against a DynamicsCompressorNode of the page | rms +-0.02; reduction +-1.5 dB against the page node, +-0.12 dB between engines (+-0.3 dB for a nothing-to-compress case) |
| WaveShaper | identity, half, clip, soft and inverted curves, an empty curve, oversample NONE / 2X / 4X (energy above 8 kHz) | rms +-0.02, harmonics +-0.03, band rms +-0.01 |
| Convolver | single impulse, two impulses (computed from the sample rate), 10 ms late impulse, normalize | rms +-0.01, lag +-0.004 s |
| BufferAudioSource | 500 Hz sine from numbers; playbackRate 2, detune 1200, gain, pause/resume, loop, stereo, a data: wav url | rms +-0.02, f0 relative 0.004, url rms +-0.015 |
| ChannelMerger / Splitter / Selector | pure tones in the right channel only; disabled behaviour | rms +-0.02, silent channels +-1e-4 |
| SpatialSound | left, right, front, linear, exponential, intensity, cone, reference distance against the stereo panner formulas | rms +-0.012; HRTF +-0.004 between engines |
| ListenerPointSource | listener position / forward / up read from the AudioListener; the panner level for five poses | position and axes +-0.01, rms +-0.012 |
| AudioDestination | gain 0.5 / 1, disabled (silent, isActive false), enabled again; mediaDeviceID default / unknown / empty | rms +-0.02, silent +-1e-4 |
| MicrophoneSource | fake 1 kHz microphone rms 0.3536, gain 0.5, pause, resume, stop, restart, disable | rms +-0.03 (+-0.02 gain), f0 +-3 Hz |
| StreamAudioDestination / Source | loop through the stream: rms 0.7071, gain 0.5, disable, rename, pause, unknown name, late stream, page made 440 Hz stream (our reader only) | rms +-0.03 (+-0.02 gain), f0 +-3 Hz |

## Fixes that the signal test forced in the reader

- `PeriodicWave`: a live change of `real` / `imag` / `type` now reaches the running oscillators.
- `OscillatorSource`: `gain` applies while the oscillator runs.
- `SpatialSound`: a property change no longer disconnects every other listener of its output; a disabled SpatialSound is silent at its output (X_ITE: the same), not only at the loudspeaker.
- `AudioDestination`: `mediaDeviceID` selects the output through `setSinkId` (see 11).
- `StreamAudioDestination`, `StreamAudioSource`: real streams (see 12).
- Test rig: `getUserMedia` wrapper, AudioWorklet taps, `amap` (not `jsmap`), unit test 28 keeps loading the shared runner without a page (`window.AUD`).

## What remains

- Real devices: which loudspeaker a `mediaDeviceID` reaches, and a real microphone, cannot be tested in headless Chromium.
- Time responses: DynamicsCompressor attack and release as a curve, Analyser smoothing as a curve, Delay with a changing delayTime (the click), BufferAudioSource and OscillatorSource start-up latency at sample accuracy. Only settled values and onsets within about 6 ms are compared.
- Noise floors and the spectrum between peaks of the Analyser; filter phase response (only the magnitude); Convolver stereo and 4 channel responses; more than 32 children or outputs.
- HRTF against a formula (Web Audio gives none; it is compared with X_ITE only); SpatialSound `dopplerEnabled` and `priority` are held (Web Audio dropped the Doppler effect).
- Streams: a stream from the network (a real WebRTC connection) was not built; the page connects it through `BR.snd.streams`.
- X_ITE plays a SpatialSound only while drawn and gives the 4.0 ListenerPointSource none of its clock; the bridge does not copy either and the specs say so.
- A long test (BiquadFilter has 278 steps) takes about 3 minutes per engine pair on the rig; the whole Sound component is about 12 minutes, three processes in parallel.
