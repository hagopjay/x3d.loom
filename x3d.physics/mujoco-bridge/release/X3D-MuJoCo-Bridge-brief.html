FIELD NOTES · Nº 1 · X3D ⇄ MUJOCO

A briefing for colleagues · 7 November 2026

An open bridge between two worlds

One language for how things look.
Another for how they move.

X3D is the ISO-standard, web-native format for 3D scenes. MuJoCo is the physics engine robotics researchers trust. They have never spoken to each other. We built the bridge, and it runs entirely in a web browser, with nothing to install.

§1

What it does, live

A robot arm pushes into a ball. The two engines narrate it.

§2

Why both communities should care

Each side gains what it can't easily build alone.

X3D gains

A real dynamics engine without inventing one, and a standard place to author physical parameters (masses, lengths, contacts) inside an open, inspectable scene format.

MuJoCo gains

A standard, browser-viewable presentation layer, not just for models but for whole experiments: scene, sensors, commands and results travel together.

Researchers gain

Reproducible experiment packages. A reviewer opens one ZIP in a web page, sees the same scene, re-runs the trial and checks the numbers.

§3

The one design rule

Every value has exactly one owner.

X3D owns

  • how everything looks
  • what you click and drag
  • what you want: goals, edits
  • units, labels, stable ids

MuJoCo owns

  • where things actually are
  • speeds, forces, collisions
  • sensor readings
  • the clock

The 3D scene only asks; the physics engine only answers. Every request carries an id and the version of the world it was meant for, so a stale request is refused rather than quietly applied. Changing a goal is an instruction. Moving the ball changes the world, so MuJoCo recompiles it and says so. The contract (x3d-mujoco/0.1) is versioned and has JSON Schemas.

§5

For AI assistants too

An assistant can now build, check and run physics experiments.

"Turn this pendulum into a 3D scene."

mjcf_to_x3d → valid X3D, 0 errors. Losses listed: 2 joints, 1 keyframe, dynamics.

"Push the arm into the ball and save the experiment."

simulate → 2,500 steps, 1 contact, package saved · validate_scene → consistent.

"Load this: <include file="/etc/passwd"/>"

Refused: <include> reads other files.

Condensed from a recorded session with the real tools.

Three tools speak the bridge contract through the Model Context Protocol, the standard way AI assistants use software. They live alongside X3D validation in one server:

validate_scene checks a scene or experiment package.
mjcf_to_x3d turns any MuJoCo model into an X3D scene and reports what it lost.
simulate runs it and returns the measurements.

No conversion ever claims to be perfect: every one returns a machine-readable loss report.

§6

The path to planet scale

From one laptop to tens of thousands of researchers a day.

Why it can be cheap

The costly part of physics is the simulation loop. It runs in each visitor's browser, so more visitors add almost no server cost.

Servers do only what browsers can't: batches of thousands of rollouts, long jobs, converting big model libraries. That part is metered, and GPU sweeps sit behind their own quota.

Scale is mostly trust

Correctness, reproducibility, security and versioning first. That is why phase 0 was tests, a licence and a threat model.

Old results keep working

Each package pins its engine build; old builds are kept, so a 2026 paper still replays in 2036.

No single codebase to trust

The end state is an open spec, a conformance suite anyone can run, and an independent second implementation.

§7

Honest limits

What it isn't, yet.

  • Not a universal translator. One carefully described arm today; general MuJoCo ⇄ X3D (with a public scoreboard over MuJoCo Menagerie) is phase 1.
  • Not X3D's own physics. X3D has a RigidBodyPhysics component; we don't claim to implement it. MuJoCo is the authority.
  • Not bit-for-bit replay yet. Records are observations. Exact checkpoints come in phase 1.
  • The GPU notebook is a sketch. It is written and checked, but hasn't been run on a GPU yet.

What I'd love from you
