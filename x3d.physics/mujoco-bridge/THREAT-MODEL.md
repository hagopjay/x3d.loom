# Threat model: the bridge importer

Phase 0, step 6. Covers every place untrusted bytes enter the bridge: the browser importer (`readScene` in `src/bridge/scene.ts`, `importBundle` in `src/bridge/package.ts`), and the MCP tools added in the agents slice (`x3d_mcp` fork, local branch `bridge/agents-slice`).
Tests: `npm run verify:threats` (`scripts/verify-importer-threats.mjs`, record in `validation/importer-threat-results.json`), part of `npm test`. Each check is labelled **defended** (an assertion that the attack fails) or **gap** (it measures today's weak behaviour, so a fix shows up as a test change).

## Assets and attackers

Year one is local only (browser, CLI, MCP over stdio), so there is no server to take down and no other users' data to steal. What is at risk:

| Asset | Why it matters |
|---|---|
| The researcher's machine: files, memory, CPU | a hostile scene or package is opened *on their machine*, in their browser or through their agent |
| Integrity of an experiment | a package that silently says one thing and simulates another poisons results that get cited |
| The agent's context | an MCP tool returning attacker-controlled text is a prompt-injection path into a hosted model |

| Attacker | Capability |
|---|---|
| A shared `.x3d` or experiment `.zip` (email, a repository, a paper's supplementary material) | full control of the bytes the user imports |
| An MJCF model handed to `mjcf_to_x3d` or `simulate` by an agent, possibly fetched from the web | full control of the XML, plus any filenames it references |
| Later (phase 3, hosted): any anonymous uploader | the same bytes, now on *our* servers, many at once |

Out of scope for now: a compromised npm or PyPI dependency (supply chain), malicious browser extensions, physical access.

## Threats, current defences, evidence

| # | Threat | Current reader | Evidence |
|---|---|---|---|
| T1 | **XXE**: an external entity (`<!ENTITY x SYSTEM "file:///etc/passwd">`) reads local files or makes requests | **Defended.** Any `<!DOCTYPE` or `<!ENTITY` (case-insensitive) is refused *before* parsing. Browsers' `DOMParser` doesn't fetch external entities either way (second layer) | X1, X3 |
| T2 | **Entity expansion** ("billion laughs") exhausts memory | **Defended** by the same pre-parse refusal (0.02 ms) | X2 |
| T3 | **Oversized XML** | **Defended**: over 200,000 characters is refused before parsing, and a file over 2 MB is refused before it is read | X4, `BridgeApp.tsx:57` |
| T4 | **Script and active content**: Script, Inline, EXTERNPROTO, ProtoInstance, Anchor, textures with URLs, `on*` handlers | **Defended**: an allow-list of 25 script-free node types, and any `on*` or `url` attribute is refused. Imported XML is **never rendered**: only the recipe and target are extracted, and the displayed scene is regenerated by `createScene` | X5, X7, Z7 |
| T5 | URL-bearing fields with other names (`Background.backUrl`, …) | **Gap, harmless today.** The lexical filter only knows `url`, but the value never leaves the importer (X10 asserts it isn't in the output). It becomes a real risk the day imported presentation is rendered (the "preservation path" in phase 1). Fix then: allow-list *fields* per node from X3DUOM, not just nodes | X10 |
| T6 | **Giant meshes** (millions of vertices) | **Defended by scope**: no mesh geometry node is in the profile | X6 |
| T7 | Deep nesting and CPU blow-up | **Gap (minor).** 5,000 nested Transforms within the size cap took 1.7 s in jsdom. Fix: a depth limit (64) and a node-count limit in `readScene` | X11 |
| T8 | **Non-finite or out-of-range physics** (NaN, 1e308, negative mass) that crash or destabilise MuJoCo | **Defended**: `parseRecipe` bounds every value and needs it finite | X8 |
| T9 | **Prototype pollution** through the embedded manifest JSON | **Defended**: `JSON.parse` makes `__proto__` an own key, and `parseRecipe` copies only known fields | X9 |
| T10 | **ZIP bomb (honest headers)** | **Defended**: a member declared over 5 MB, or a declared total over 12 MB, is refused before inflating; a package over 2 MB is refused outright | Z1–Z3 |
| T11 | **ZIP bomb (lying headers)**: headers under-declare the real size | **Gap.** The pre-check trusts the header; JSZip inflates the whole member, then throws "uncompressed data size mismatch". Measured: a 34 KB package inflated 30 MB (about 94 MB peak extra memory) before rejection. Estimate: the 2 MB cap allows about 2 GB (deflate tops out near 1032:1), enough to crash a tab. Fix: inflate with a streaming decoder that stops at the declared size, or at most 5 MB (fflate's streaming `Inflate`, or JSZip `internalStream` with a running byte count) | Z8 |
| T12 | **ZIP path traversal** (`../../evil.sh`, absolute paths) | **Defended by design**: import works in memory, reads exactly three fixed member names and never writes to disk. Z4 runs inside an empty temporary directory and asserts it stays empty | Z4 |
| T13 | **MJCF `<include>`, plugins and asset files inside a package** | **Defended**: `mjcf/model.xml` must equal, byte for byte, the MJCF regenerated from the recipe, so a package can't smuggle in its own MJCF | Z5 |
| T14 | **Inconsistent package** (manifest says one thing, scene another) | **Defended**: refused, with no silent preference for either | Z6, the existing tamper test in `verify-bridge.mjs` |
| T15 | **Silent substitution of a trial record** (`records/*.json`) | **Not checked.** Records are observations, not inputs, and import ignores them. Once replay exists (phase 1), packages need content hashes of each member in the manifest and a replay check | none yet |

## The MCP tools (Python, agents slice)

These accept *arbitrary* MJCF and X3D from an agent, a wider surface than the browser's curated profile. As built on branch `bridge/agents-slice` of the x3d_mcp fork (`src/mujoco_bridge/safety.py`, `src/tools/bridge_tools.py`; tests in `tests/test_bridge_tools.py`, 31 passing):

1. **XML parsing**: any DOCTYPE or ENTITY is refused before parsing; lxml then runs with `resolve_entities=False`, `no_network=True`, `load_dtd=False` and `huge_tree=False`. Input is capped at 2 MB.
2. **MJCF**: compiled from a string (`MjModel.from_xml_string`), so there is no base directory. Refused before compiling: `<include>`, `<plugin>`, `<extension>`, `<instance>`, `<model>`, and every file attribute (`file`, `meshdir`, `texturedir`, `assetdir`, cube-map `file*`). No plugin library is ever loaded on request.
3. **Size limits** after compiling: 200 bodies, 1,000 geoms, 50,000 mesh vertices. `simulate` allows at most 100,000 steps.
4. **Time**: `simulate` checks a wall-clock budget every 100 steps (default 30 s, at most 120 s) and returns partial results marked `truncated: true`.
5. **X3D bridge scenes** use the browser's node allow-list with two stricter rules that close T5 and T7 for the Python path: any attribute whose name ends in `url` is refused (so `backUrl` is too), and nesting deeper than 64 is refused.
6. **Packages**: an honest ZIP bomb is refused from its declared sizes (5 MB per member, 12 MB in total, 2 MB compressed). A **lying** ZIP is refused *without* inflating it: Python's `zipfile` reads only the declared size and then fails the CRC check (T11 measured as closed on this path; the 5 MB cap is a second guard). Member names are listed, never extracted.
7. **Files**: `path` arguments read any local file up to 2 MB, like x3d_mcp's existing `load_x3d_source`, and are disabled over the HTTP transport. `package_out` writes only a **new** `.zip` into an existing directory (it never overwrites) and is also disabled over HTTP.
8. **Output to the agent**: structured JSON. Names that came from the input are capped at 64 characters; samples are thinned (`max_returned_samples`, 60 by default) so one call can't flood the agent's context.

## Phase 3 (hosted), recorded now so it isn't forgotten

Everything above assumes the attacker's bytes run on the attacker's victim's own machine. Once a service parses uploads: parse and simulate in a sandbox (gVisor or Firecracker, no network, cgroup memory and CPU limits, a time limit per job); never accept native plugins; content-hash every stored member; rate-limit per ORCID account; run the T11 fix (streaming inflate with a hard cap) before anything is exposed.

## Priority fixes (not made in phase 0; listed in GATE-0)

1. T11 lying-header ZIP: bounded streaming inflate. Small change; the Z8 check flips to `defended`.
2. T7 depth and node-count limits in `readScene`.
3. T5 per-node field allow-list from X3DUOM, needed before any presentation preservation.
4. T15 member hashes in the manifest (with replay, phase 1).
