# What the X3D Chess lenses teach (18 Nov 2026)

Source: https://github.com/hagopjay/x3d.chess, PR #6 (review package, merged) and PR #7 (lenses, branch `claude/project-thread-2j8j26` at 9eb14e9), folder `viewer/js/{terrain,concepts,inspector,branches,skyline,lenses}.js`, docs `docs/LENSES.md`, receipts `evidence/lens-smoke.json`. Rig for every number: Chromium 153.0.8010.12 with software GL (SwiftShader), Playwright 1.63.0, X_ITE 16.6.1 vendored locally, Node 22, python-chess 1.11, vendored Stockfish 19 lite single-thread WASM. No GPU, no frame-rate claim. Grades follow the Loom: C = confirmed by a run, L = likely, S = suspected.

## 1. Findings

| # | Finding | Grade | Evidence | Rule it suggests |
|---|---|---|---|---|
| 1 | **Parity with your own twin is agreement, not truth.** The inherited Python and JavaScript detectors agreed on 650 positions (0 mismatches) while still reporting wrong pins and discoveries; independent answers found what parity could not | C | x3d.chess `docs/RESULTS.md` (parity row and the five quirks), review package F04 | Write the known answers from a different instrument first (python-chess, a hand-derived position), then regenerate parity |
| 2 | **Every lens module was checked against an independent oracle, and a per-module adversarial review still found real defects**: 20 confirmed and fixed, each with a regression test that failed on the old code. Examples: `groupFlat(arr, 0)` loops forever; a UCI `wdl` field made a lowerbound read as exact; arc apexes sat off the drawn path; a duplicate rank was labelled but never drawn; defender rays were dimmed as if the move were illegal; a -5 cp score was drawn above the baseline and labelled "0.0"; a reported 0 cp vanished on the ribbon; concept flags spilled onto neighbour squares | C | five module tests: terrain 609 checks, concepts 50,112 checks over 327 positions, inspector 100 positions x 64 squares, skyline 3,360 checks, branches 9 groups with real Stockfish MultiPV 3 depth 8 on 3 FENs | Oracle first, then one reviewer whose only job is to break the module; keep the failing input as the regression test |
| 3 | **A live stream makes asynchronous analysis stale by construction.** The first native run asked for MultiPV on the focused board and every result was dropped because the game had moved: "The board moved before the search finished" | C | first `tools/lens-smoke.mjs` run, step `engine-lines` | Pause the one game being analysed (`holdGame`/`releaseGame`), search the held FEN, bind every result to its searched FEN, and drop a result for any other position |
| 4 | **An overlay module must not import its host.** `board.js -> lenses.js -> branches.js -> board.js` made a top-level `const` read before initialization (`Cannot access 'BRANCH_LEGEND' before initialization`) and failed three suites; the fix was two local copies of a four-line helper | C | `npm test` failure, then pass (24 checks) | Overlay modules import data and chess.js only; the host imports them, never the reverse |
| 5 | **Picking a square needs the hit point, not the touch.** A TouchSensor only says "touched". Adding an outputOnly `hitPoint` PROTO field (IS `hitPoint_changed`) let the page compute the file and rank; a real mouse click then inspected d4. Effect shapes stay `pointerEvents='false'` so they never hide the sensor | C | `lens-smoke` step `inspector-click`; XSD validation of the regenerated grid | Expose the pick point through the PROTO interface, keep every overlay shape out of the pick |
| 6 | **A 3D chart needs its own camera.** The skyline plane at y = 4 was outside the overview frustum, so the first picture showed empty sky; a dedicated oblique pose (`rig.skyline()`) framed eight columns and their labels | C | screenshots before and after (`docs/assets/lens-skyline.png`) | Every overlay that lives off the board plane ships a camera pose and a screenshot proving it is in frame |
| 7 | **White-perspective scores look unsorted when Black moves.** MultiPV line 1 read +0.56 and line 2 +0.63 for the same position: line 1 is Black's best, and Black prefers the lower White-side score. Labels now say "White POV" | C | `lens-smoke` step `engine-lines` labels | Always print the perspective beside a score; never sort a White-POV list by value without saying whose preference orders it |
| 8 | **A native browser run found nothing the Node suites could, and still had to run.** The review package declared the native gate `not_run`; here it ran in about 25 s and passed (replay 20 boards: 636 pieces, 0 misplaced; wasm 4 boards depth 8: 111 pieces, 81 moves; study room) | C | `evidence/browser-smoke.json` and `tools/smoke.mjs` receipts | Run the native gate wherever a browser exists; label what it cannot say (software GL, no frame rate) |
| 9 | **Test runs rewrite tracked receipts.** `npm test` changed `evidence/*.json` and `examples/x3d/*.x3d` timestamps and hashes each time | C | `git status` after the run | Treat receipts as outputs: commit them from one deliberate run, and keep sources stable between runs (the repo's own `source-stability` check enforces this) |

## 2. Reusable pieces

* `viewer/js/lenses.js`: `BoardLens` (single-flight mount per overlay, per-lens revision plus board epoch, paint synchronously after the last await) and `SkylineLayer`; copy the pattern for any overlay that updates from an async stream.
* `tools/lens-smoke.mjs`: one Playwright script that drives every lens through its real button and key, including a mouse click, and writes a JSON receipt and screenshots.
* `tools/concepts_gen.py` and `tools/inspector_expect.py`: fixed-seed python-chess oracles that write the expected answers the JavaScript test must match.

## 3. What this does not prove

* No hardware GPU, no frame rate, no Firefox or Safari, no native Windows Stockfish; the engine here is the vendored WASM build.
* Concept definitions are conservative counting rules, not strategic verdicts; SEE is a static estimate.
* Engine lines need the browser engine arena; the UCI-server transport has no analysis endpoint yet.
