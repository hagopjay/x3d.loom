# X3D to three.js bridge (scaffold)

A three.js drawing half for the reader that the Babylon bridge ([`../../x3d.webgpu/bridge`](../../x3d.webgpu/bridge)) already owns. Nothing under `x3d.webgpu/` is copied or changed: `tools/bundle.js` reads the reader, kit and node files from there at bundle time, so a fix to the reader reaches both bridges.

How hard is the port, group by group: [ESTIMATE.md](ESTIMATE.md). Node-by-node state: [NODES.md](NODES.md) (generated). Why each choice was made: below and in the headers of `src/body-three.js` and `tools/run-tests.js`.

## Run it

```sh
npm ci                                   # three, x_ite; playwright is expected on the machine (NODE_PATH) or installed
node tools/run-tests.js Box Switch BooleanToggle      # one JSON line: ours vs X_ITE, per step
node tools/run-tests.js --shots .shots Sphere         # keep both pictures and the side-by-side inputs
python3 tools/driver.py check Box Sphere              # run, write receipts/NODE.json, update NODES.json and NODES.md
python3 tools/driver.py next 10                       # the next ten nodes that need the body
python3 tools/driver.py status
```
Env: `XITE_DIR` (X_ITE `dist/`), `THREE_DIR` (three `build/`), `CHROMIUM_EXECUTABLE`. Fixtures are looked up in `fixtures/` (scene fixtures for this body) and then in `../../x3d.webgpu/bridge/fixtures/` (event fixtures every body shares).

## The choices, and why

1. **Share the reader, replace only the body.** The reader holds no engine call; the Babylon `Body` is about 1,670 lines and the three.js one about 280 for the same core (461 after batch 2, with 30 more drawn nodes). A second bridge that forked the reader would fall behind it.
2. **Colour management off, linear output.** X3D colours are authored numbers and X_ITE 16.6.0 writes them as they are. Matching that makes the comparison honest; `opts.srgb` switches to the managed path as one flag, not a hidden default. The authored-sRGB question for lighting quality is the owner's call and stays open here.
3. **Lights times PI.** since r155 three.js lights are in physical units: intensity 1 gives diffuse/PI. X3D wants diffuse x intensity x N.L, so every light carries a factor PI (`THREE_PI`).
4. **Phong exponent x4.** X_ITE evaluates Phong with the reflection vector; three.js uses Blinn-Phong, which needs about four times the exponent for the same highlight (`opts.shininessScale`). Measured: Sphere 28.2 to 37.0 dB, Box 63.8 to 70.1 dB by that change alone [C].
5. **No winding flip, no handedness flag.** X3D and three.js are both right-handed, Y up, counter-clockwise front. Babylon needs `useRightHandedSystem` and a `sideOrientation`; here `solid=FALSE` is just `DoubleSide`.
6. **Transform is one matrix.** T C R SR S -SR -C keeps a shear; the Babylon body decomposes to TRS and logs the loss.
7. **The first Viewpoint is bound at load** (19775-1 23.4.1). The first run drew at the default pose and missed X_ITE by IoU 0.34 to 0.64 on every fixture until this was added; with it, 1.00.

8. **Shader chunks patched, once, with the X3D formula** (`patchThreeShaders`; a replace that finds nothing throws, so a three.js upgrade fails loudly): point and spot `radius` is a hard edge (three.js dims with a window), the spot cone is a linear ramp in the angle (three.js: smoothstep over cosines), fog uses the distance to the eye and X_ITE's LINEAR and EXPONENTIAL formulas (three.js: view depth and smoothstep), attenuation is the polynomial normalised by a0 (`decay` carries b2 or minus b1). Measured against X_ITE: SpotLight 63.1 dB, PointLight 36.3 to 51.2 dB, Fog 46.6 to 53.4 dB, attenuation 59.2 dB.
9. **Lights are children of their parent group's object**, so a Transform above a light moves and turns it with no refresh.
10. **UV conventions, found by reading X_ITE 16.6.0 and checking the picture:** Sphere u = 0 at -Z growing toward -X; Cylinder and Cone the same, with planar cap images; TextureTransform is the matrix `-C S R C T` read as a column matrix, not the T C R S -C order of Transform (50.1 dB against 21.3 dB for the wrong order). Box needed nothing (99 dB).

## Known gaps (also in each spec's `gaps` and `scope`)

`global=FALSE` lights light the whole scene; material `ambientIntensity` is a fixed 0.2; attenuation with both a1 and a2 non-zero is a fit, not exact; MovieTexture, PointProperties, FloatVertexAttribute and the shader stages other than vertex and fragment, Sound, HAnim, particles, Texturing3D, TextureProjector, the Nurbs family and Volume are not drawn yet; the cube maps, the pointer sensors (TouchSensor, GeoTouchSensor, Plane, Sphere, Cylinder, Key, String) and ComposedShader are (batch 4), CAD and Geospatial (batch 5), the Picking component (batch 7: PickableGroup and four pick sensors, ported from the shared tests in `kit.js` onto three.js meshes in `nodes/Picking.js`), Layering and Layout (batch 6: a layer has no lights, Background, NavigationInfo or Viewpoint binding of its own, `activeLayer` is held, and a pick sensor in a layer sees only the shapes of its own layer); TextureProperties: CLAMP and CLAMP_TO_BOUNDARY clamp to the edge (no border colour), textureCompression and texturePriority are read and ignored; MultiTexture composes the stages on a 256 x 256 canvas (8-bit, the Babylon body does the same), ADD stages are summed on a second canvas and added before the light, the other modes are the canvas blends (a mode outside REPLACE / MODULATE / MODULATE2X / MODULATE4X / ADD is drawn as MODULATE); TwoSidedMaterial is two meshes on one geometry (front, back) and has no ambient term; LineProperties draws a line linewidthScaleFactor pixels wide as screen-space quads (butt ends, no joins, no fog) and linetype is not drawn; the camera-space TextureCoordinateGenerator modes redo the uv of every vertex on the CPU in the frames in which the view or the mesh moved; Background draws the sky and ground as vertex-coloured spheres (one colour per ring of 48 steps) and ignores set_bind between several Backgrounds; LocalFog fogs by the nearest group that holds an enabled one, with the fog object swapped per mesh at draw time; FillProperties hatching is a screen-space overlay, 32 x 32 masks lifted from the Babylon body; OrthoViewpoint zoom scales the view box (the Babylon fixtures NurbsCurve, NurbsPatchSurface and Polypoint2D match X_ITE in the picture, IoU 1.00 and 0.99+, but their later steps call Babylon-only helpers (`getTotalVertices`, `window.__mouse`); 32 of the Babylon fixtures probe `__body.rec`, `scene.lights` or `geometryData` and run here for their pictures only) (`body-three.js` notes `skipped <Node>`); PhysicalMaterial is the glTF model and X_ITE lights it with a default environment glow that three.js has no counterpart for (the fixture is reference-only, IoU 0.91); IndexedLineSet colours follow coordIndex only (the reader has no colorIndex for it) and ColorRGBA alpha is not drawn; a ClipPlane keeps working after geometry or child changes (the clip list is rebuilt on every shape build); IndexedTriangleSet and IndexedQuadSet generated normals match X_ITE to IoU 0.95 (a dim rim, cause not isolated); several ClipPlanes on one mesh intersect, a disabled one adds nothing; Billboard and LOD evaluate against the camera each frame, not per picking ray; Text is a glyph atlas drawn on quads, laid out by the Babylon-reader fields (justify on the ink box, length, maxExtent, size, spacing, BOLD / ITALIC) with the Droid Serif, PT Sans and Ubuntu Mono files X_ITE ships (the body option `fontBase`); the outline boxes match X_ITE to a pixel but the letter shapes do not (IoU 0.65, 19.2 dB, `lookNote` in the fixture), vertical and right-to-left layouts are not drawn (a note is emitted) and a texture on a Text is ignored; the shared reader dropped the FontStyle `style` attribute (it is in the skip list for `style` on other nodes), a one-line change in `x3d.webgpu/demo/src/brain/reader.js` (the Babylon body reads BOLD from it; it does not read ITALIC); Inline fetches the file (gunzip when the first bytes are 1f 8b), parses it with the SAI shim and builds the roots under its own group, `load` FALSE unloads it and TRUE loads it again, a url change reloads, the urls are tried in order, a relative url is read against the file that holds the Inline, and what is inside the inline file (textures, fonts) is still read against the main file; a file that includes itself, a nesting deeper than 8, more than 512 loads in a world and a file over 32 MB (128 MB unzipped) are refused with a note (IoU 1.00, 52 to 56 dB against X_ITE for three copies); GeoLocation and GeoTransform are one 64-bit matrix per node (the world matrix stays in doubles on the CPU; a GeoViewpoint 6e6 m from the centre without a GeoOrigin is as good as the 32-bit modelView allows) and a GeoViewpoint draws with near 0.125 and far 1e9 on a plain depth buffer (X_ITE uses a logarithmic one); the pointer layer picks with a Raycaster over every visible mesh, honours ClipPlanes and the near plane, and runs hover only when the world has a pointer sensor; hitNormal is the flat face normal of the triangle; no real-GPU timing exists and none is claimed.

## Adding a node

`driver.py next 10`, then write a fixture and spec (copy the nearest in `fixtures/`), then add `src/nodes/NODE.js` to this tree: it registers `R.bridge.three.build.NODE(body, n, parent, chain)`, `R.bridge.three.geometry.NODE(g, body)` (return a `BufferGeometry`) and `R.bridge.three.changed.NODE(body, n, field)`. The Babylon node file is not touched; the reader half it already carries (field table, ROUTE behaviour) is reused as it is. Then `driver.py check NODE`. A node whose Babylon file only returns vertex data (`geometry` hooks, `lines`, `points`) needs nothing at all: the body calls the shared hook and wraps the arrays (batch 2 drew eleven nodes that way, seven through `geometry()` and four through `lines()`, with a fixture each). A node the reader does not define (TriangleSet, ElevationGrid here) is defined in this tree with `BR.node(...)` and its own `geometry()`; check `grep -n NODE x3d.webgpu/demo/src/*/reader*.js` first, because the Hall reader already turns Extrusion, Rectangle2D and Disk2D into an IndexedFaceSet at parse time.
